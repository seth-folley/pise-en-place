01 / THE DESIGN CHOICE

A message broker, not a shared scratchpad.

Use one small per-user broker, persistent Unix-domain socket connections, and broker-owned SQLite storage. Each Pi session loads a coordination extension. Agents exchange explicit messages through tools; the broker routes them into durable participant mailboxes.

The important upgrade is ownership, not file format.

SQLite is still stored in files and uses locks internally. The difference is that agents no longer compete to rewrite shared state. One service owns transactions, ordering, identity, and recovery. Sessions communicate through a versioned protocol, never by editing the database.

02 / WHO TALKS TO WHOM

One connection per session. One authoritative service.

The agents are peers. The broker is infrastructure, not a manager and not an LLM. An optional moderator joins through the same extension as everyone else.

The agent reasons

Chooses a recipient, asks a concrete question, cites artifacts, replies, or proposes a decision. It does not implement transport retries or continuously poll an inbox.

The extension adapts

Binds the current session, exposes tools, renders notifications, and inserts attributed peer messages at safe Pi boundaries. It owns local pause and abort handling.

The broker guarantees

Validates membership, stores accepted sends, orders threads, manages delivery records, and serializes policy changes. It never executes an agent’s shell commands.

Identity is explicit, not inferred from a directory.

Join a named coordination project and choose a participant name/role. The broker assigns immutable project and participant IDs. A live binding includes the Pi session ID and a monotonically increasing connection generation; stale connections cannot mutate state. Duplicate names never silently take over a participant.

Reload may restore the same identity with a fresh generation. New/resume/fork/clone detach by default and require explicit rejoin; process-restart automatic rejoin is a separate opt-in. Heartbeats provide observed presence, not proof that the model is making progress. Self-reported blockers remain a separate field.

02A / MULTIPLE TEAMS · SEPARATE ROOMS

One broker does not mean one big team.

Agreed direction: multiple teams can run concurrently, each with its own explicitly joined room and specific participants. A team is the user-facing name for a coordination project in the requirements; the room’s immutable ID is the protocol’s projectId. Repository paths do not determine membership, and sharing a broker never enrolls sessions in a common conversation.

Room-scoped everything

Validate membership and room ownership on every send, read, receipt, subscription, redirect, decision, and authority operation. Reject a recipient/thread/decision from another room even if the caller belongs to both. Participant identities and roles belong to a room; the same display name can exist independently in different rooms.

Pausing, leaving, or resetting a room’s limits does not change another room. Reconnecting restores only valid, explicitly enrolled bindings. Broker failure can affect every room’s transport, but never merges their history.

Logical rooms, not separate daemons

One persistent socket per Pi session can multiplex authorized room subscriptions. The connection carries explicit room IDs; the broker maintains separate room-bound participant/session generations and mailboxes. Separate processes or socket files per team are not required for this isolation.

Redirection stays within the original room. Moving information to another room would require a separate explicit send, with provenance, rather than silently moving a thread or forwarding room announcements.

Additional proposal: one session may explicitly join multiple rooms

Running several teams across different sessions is required. Supporting several memberships in a single Pi session avoids a singleton “current team” constraint as well. A second join would add a room, not replace the first. Each membership gets its own participant identity, role, mailbox, wakeup policy, and local pause. A session-wide pause can stop all its coordination delivery.

  • Always scope agent actions. Agent tool requests include an explicit room ID. Reply and thread relationships are checked against it. No destination is inferred from whichever team most recently sent a notification.
  • Keep human commands unambiguous. Proposed syntax: /team join <room>, /team status [room], /team inbox <room>, and /team leave <room>. Bare status shows joined-room summaries and lets the user inspect one. For mutations, require a room or show a room picker when ambiguous; do not silently act on every team.
  • Serialize access to the model. One Pi session still has one agent run at a time. Fairly schedule eligible messages across joined rooms at safe boundaries; enforce each room’s budgets plus a session-wide activation bound. Receiving traffic from several rooms is not permission for parallel model runs or an aggregate budget bypass.
  • Label all content and notices. Include the room name and stable identity in messages, approval reviews, unavailable-recipient notices, and reconnect summaries. Only show the widget’s rooms that this session has joined, not all rooms hosted by the broker.
Shared session means shared model context.

Broker routing isolation cannot prevent a model enrolled in two rooms from remembering content from both. Use separate Pi sessions when teams need context separation. Multi-room membership is explicit and must warn about this boundary; it is not a mechanism for confidential compartments inside one model context.

Isolation tests: run two rooms simultaneously; reject cross-room IDs and subscriptions; allow identical names without identity collision; verify room pause/leave/reconnect and grants remain scoped; verify status excludes unjoined-room metadata. If multi-room sessions are enabled, test explicit routing, fair scheduling, aggregate limits, and that a second join preserves the first membership.

03 / A REAL EXCHANGE

Send now. Receive safely. Reply later.

Example: the backend asks whether missing flight numbers should be represented as null. Its send finishes after a database commit—not after the app agent thinks about the answer.

What travels over the socket?

Proposed protocol v1: bounded UTF-8 JSON frames delimited by LF, with request IDs for responses and separate server events. Persistent bidirectional connections carry sends, reads, receipts, presence, and mailbox-change notifications. Framing must tolerate partial/coalesced socket reads and reject oversized frames before unbounded buffering.

Handshake negotiates protocol version and authenticates the registered client. Subscriptions are project-scoped; reconnect performs a pending-mailbox sync. Push events are hints, not a second source of truth.

04 / RELIABILITY WITHOUT MAGICAL GUARANTEES

“Sent” is not a single state.

Keep message acceptance separate from per-recipient delivery, and delivery separate from understanding or task completion.

StoredMessage committed by broker.
→
Pending deliveryDurable recipient mailbox entry.
→
Queued locallyRecipient adapter or Pi queue accepted it.
→
Context recordedInsertion observed in recipient session.
→
Explicit ACKAgent acknowledges; resolution is a separate action.

Pending and later delivery states belong to each recipient, not the whole message. Cancelled/expired deliveries remain visible. A queued local copy may disappear on crash; a context receipt does not mean the model understood, acted correctly, or still retains the message after compaction.

Transactional mailbox / outbox

Store the message, thread sequence, and all recipient delivery rows in one transaction. Delivery rows are the durable dispatch queue; notify clients only after commit. A broker crash between commit and push loses no accepted message.

Use SQLite WAL with durability settings appropriate for successful-send guarantees (proposed synchronous=FULL), foreign keys, uniqueness constraints, and transactional revision checks. No need for a separate queue product or full event-sourcing framework.

At-least-once transport, stable logical identity

Retries reuse message/delivery IDs. The extension deduplicates before insertion and records IDs in custom-message details. Old connection generations are fenced out.

Only claim what can be observed. pi.sendMessage() returning is not itself a durable-context receipt. A persisted message is also not proof of exactly-once model execution.

Recovery rules worth agreeing on before coding
  • Lost send response: retry the same idempotency key or query its result. Timeout means unknown acceptance, not guaranteed failure. No silent offline sender spool in the first milestone.
  • Offline recipient: retain pending messages until explicit cancellation/expiry policy. Reconnect the same enrolled participant; reassignment to a new participant is a human action with an audit trail, not name matching.
  • Broker restart: reconnect with bounded backoff and jitter, validate the protocol, rebind identity, and synchronize pending state. Automatic wakeups fail closed until policy is known.
  • Compaction/tree navigation: external messages and decisions never roll back. Inspect local historical receipt IDs for deduplication, but do not confuse an entry on an old branch with current model context. Fetch relevant records on demand rather than replaying history.
  • Ephemeral session: broker history remains durable, but local context reconciliation may be impossible after a crash. Surface uncertain outcomes; do not claim durable recipient recording without evidence.
  • Storage/migration failure: return an actionable error and preserve data. Never reset the database automatically to make an incompatible client work.
05 / TRANSPORT IS NOT PERMISSION TO THINK

Push notifications. Pull context. Bounded wakeups.

A socket can receive data while an agent is executing tools. That must not imply the peer can interrupt the run or spend unlimited tokens. The extension is the final gate between mailbox and model context.

1. Manual first · default

Show a compact unread/pending notification. Deliver selected messages on user request. Optional next-user-turn delivery can use Pi’s nextTurn semantics; it does not start a run.

2. Automatic follow-ups · opt-in

At an idle/settled boundary, claim an eligible delivery and reserve a bounded activation. Use an attributed custom message with supported follow-up/trigger options. Routine work never steers an in-flight run.

3. Urgent steering · later

Explicit restricted option only. Not necessary for the first milestone. It can never bypass pause, limits, or authority. Pi steering still respects supported tool boundaries.

  • Keep routine messages broker-side until dispatch. Do not preload an irrevocable chain of Pi follow-ups while busy. Observe agent_settled and recheck ctx.isIdle(); agent_end alone is insufficient.
  • Budget transactionally. Proposed starting point: four automatic activations per thread, plus a project-wide time-window cap and pending-queue byte/count limits. One automatic recipient run consumes one reservation, not one socket notification. Exhausted limits latch until human reset; reconnects and broker restarts do not refill them.
  • Pause has a defined boundary. Serialize dispatch authorization with broker policy updates, and recheck the local gate immediately before insertion. A project-pause control should distinguish requested from effective while connected adapters settle/cancel outstanding permits. Already started dispatches/runs cannot be retroactively undone. Test this race explicitly before enabling automation.
  • Abort means stop retrying automatically. Mark the triggering delivery/run unresolved or uncertain; require deliberate retry. Never immediately wake the same agent again for the aborted message.
  • Bound context, not just message size. Proposed limits: 16 KiB bodies, 20-message pages, plus an overall rendered-output cap below Pi’s 50 KB / 2,000-line limit. Return continuation cursors and message IDs for omitted content. Twenty maximum-size bodies must not be dumped into one tool result.
An activation cap is not a dollar cap.

One agent run can include many model turns and tool calls. Track activation counts deterministically; report available token/cost attribution with its limitations. Unknown cost is unknown, not zero. Agents should ask once, continue independent work or mark a blocker, and never poll in an LLM loop.

06 / CONVERSATION AND AUTHORITY ARE DIFFERENT CHANNELS

Agents can agree. Only authorized actors can approve.

Chat messages provide input. Structured decision operations change a durable record. Human control operations grant or revoke authority. These are separate protocol capabilities—even if they use the same socket.

Workers proposeQuestion, options, rationale, evidence.
→
Collect inputAffected workers contribute; missing input stays visible.
→
Review revision NHuman by default; moderator only within an explicit grant.
→
Commit + notifySame outcome and authority reference for affected participants.

Conversation channel

team_send carries questions, replies, proposals, and handoffs. team_decision can propose or contribute input. “The user approved this” in a message is merely a claim; “agreed” does not change decision status.

Human control channel

Explicit user-facing review confirms the exact decision revision, grant, or revocation. The extension sends a scoped control operation, not a model-supplied approvedBy: human flag. Worker tools never expose human approval or delegation capabilities. Unsupported UI leaves requests pending.

Decision states: proposed, awaiting input, awaiting human approval, accepted, rejected, withdrawn, and superseded. Preserve revisions and rejected options. State changes require an expected revision; stale approval is rejected instead of approving a different proposal.

A moderator is an ordinary, manually joined participant with a coordination role. Acceptance additionally requires a live, bounded human grant, cited in the decision record. Spending, permissions, credentials, deployments, destructive actions, and product/scope changes remain human decisions. Unclear delegation fit escalates; natural-language scope is not a foolproof policy engine.

An accepted decision does not edit a schema, merge a PR, or deploy anything. It becomes retrievable evidence and can be exported to a repository only on explicit request. Git, contracts, and integration tests remain the implementation truth.

07 / SMALL SERVICE, CLEAR BOUNDARIES

Local infrastructure that stays out of the way.

Service lifecycle

Implemented lifecycle: joining starts or reuses the broker automatically, with no npm commands or normal manual teardown. It exits after 60 seconds without connections; idle connected agents keep it alive. A short SQLite startup transaction serializes stale-socket recovery and binding across concurrent joins. Live endpoints and durable history are preserved.

Stopping the broker pauses communication, not Pi. A failed send reports an error/unknown outcome, never false success. Health/status should expose protocol/schema versions and queue health without logging message bodies.

Storage & ownership

Proposed runtime location: <Pi user directory>/coordination/, honoring PI_CODING_AGENT_DIR. Database, socket, and any registration credentials are private to the OS user; directory mode 0700, restrictive file/socket modes.

Back up with SQLite’s consistent backup mechanism or while stopped—not by copying a live database without its WAL. Version migrations and preserve a recovery copy. Delete projects/history only with explicit confirmation.

Privacy & trust

Only explicit message bodies, metadata, references, and decisions are shared. The broker never follows arbitrary file/URL references or reads session transcripts. Enrollment respects Pi project trust; references confer no access rights.

Local transport does not mean local inference: delivered content goes to the recipient’s configured model provider. Registration credentials stay out of model-visible content.

Not a sandbox

Reject unregistered clients and cross-project IDs. Separate human-control capabilities from worker requests and audit protected operations. But agents with unrestricted same-user shell access can bypass filesystem/tool conventions.

This protects normal workflow boundaries and prevents peer text from becoming permission; it does not defend against malicious processes running as the same OS user.

Implementation belongs here: extension entry under extensions/coordination/, focused broker/protocol modules under src/coordination/, genuinely shared helpers under src/shared/, registration in package.json. Factories register interfaces only; connections/timers start after session_start or explicit action, and session_shutdown cleans up idempotently. No Pi-core changes or global source files.

08 / TEAM VISIBILITY · UI PROPOSALS

See who’s around. See what needs attention.

Agents work on their own assignments, ask when needed, and continue independent work or stop with an explicit blocker. They do not wait in a polling loop. The UI should make these asynchronous conversations visible without turning the terminal into a chat dashboard.

Agreed behavior: preserve messages and surface unavailable recipients.

Questions and replies remain stored when a participant disconnects. Notify the sending agent and surface the issue to the user, with options to wait, answer, redirect, or cancel. On a valid reconnect, the participant can immediately see its pending inbox. Immediate visibility does not bypass pause or authorize a model run.

Selected direction · Persistent, subagent-style widget + /team status

Use a compact persistent widget above the editor, visually similar to subagent summaries: a room heading with concise participant/status rows. Keep thread bodies, delivery diagnostics, decisions, and review controls in /team status. The exact subagent renderer to match should be inspected before implementation; these are layout sketches, not claims of an existing shared component. Preserve the existing footer.

Unavailable recipient · an actionable notice, not a blocking popup

  • Notify in the affected local session. The sender gets an honest tool result for new sends; later availability changes update a nonblocking notice in its terminal. Attention records are visible from other joined sessions through status. If no relevant UI is connected, preserve them for reconnect—do not pretend the human was notified.
  • Handle in-flight questions too. If a recipient leaves after a request was sent, create the same attention item while input remains outstanding. Being idle is not a failure. Paused recipients are labeled paused; reminders must not bypass pause.
  • Avoid alert storms. Propose a short, configurable grace period for unexpected disconnects, immediate attention for explicit departure, and one persistent item per affected request rather than a popup every heartbeat. An optional response deadline tracks overdue questions independently of presence.
  • Redirect only on human choice. Choose another explicitly joined participant in the same room, retain original sender and thread attribution, and audit the reassignment. If already delivered, forwarding cannot retract the old context; mark who now owns the response and notify affected participants.
  • Resolve the old obligation. A human answer, cancellation, or reassignment updates the request’s state. A late original recipient sees that outcome and should not resume stale work. Human answers are attributable input, not implicit approval of a protected decision.

Reconnect · pending messages visible immediately

Show missed history and current obligations separately. Messages answered by the human, reassigned, cancelled, expired, or already recorded remain inspectable but must not all be replayed into context. Uncertain insertion requires reconciliation or deliberate retry. Reconnecting clears the availability warning; it does not mark the question answered.

Selected UI direction, not installed features.

The persistent subagent-style widget and detailed /team status are the selected direction. Exact rendering, height bounds, counter semantics, reminder timing, and review interactions still need implementation design. Headless modes need structured status output; missing approval UI always leaves approval pending.

Additional acceptance checks: idle never appears unavailable; broker outage labels cached presence stale; disconnect-after-send creates one attention item; unread and needs-reply counts diverge correctly; redirected requests do not wake the original recipient after reconnect; manual/paused reconnect updates the UI without model execution. Manually check both themes and narrow-terminal layouts.

09 / WHAT TO SETTLE TOGETHER

Recommended decisions before implementation.

This document proposes the communication model and UI. The /team command family, persistent subagent-style widget with detail in status, and multiple isolated team rooms are the agreed direction. Durable offline messages and user-visible unavailable-recipient handling are agreed behavior. Exact subcommands, agent tool schemas, rendering, service controls, and persistent configuration remain proposals. Multi-room membership within one session is an additional explicit proposal, not required merely to run separate teams concurrently.

Transport & ownership

Recommendation: one per-user broker, Unix socket, SQLite. Accept a macOS-first transport, or choose loopback HTTP/event streaming now if Windows/browser access matters soon?

Broker startup

Resolved: automatically managed startup and idle shutdown. Explicit startup was an implementation shortcut, not the desired workflow. Maintenance commands remain optional.

Default delivery experience

Recommendation: notify + manual delivery first, then optional next-turn delivery. Automatic follow-ups remain a separate opt-in. Should normal user prompts automatically pick up pending questions?

First interface & milestone

Recommendation: the brief’s small /team command family and team_status, team_send, team_read, with the compact widget and status/attention views proposed above. Agree on exact controls before registering them. Add decision tooling after reliable two-session messaging.

First useful milestone: two terminals, one durable question and reply.

Join from different repos → send → see pending notification → deliberately deliver → reply in the same thread → restart and retrieve it. No moderator and no automatic wakeups required to prove the communication path.

Build in slices, prove the hard boundaries early.

  1. Freeze protocol v1: identity, framing, send semantics, delivery states, and chosen human controls.
  2. Broker + fake clients: persistence, idempotency, leases, isolation, reconnect, and storage failure tests.
  3. Two-session extension: manual attributable messaging, lifecycle cleanup, crash-window reconciliation, and a live smoke test.
  4. Controlled automation: pause/dispatch races, opt-in wakeups, persistent limits, and abort suppression.
  5. Decision workflow: human approval first; optional moderator grants and reviewable export second.

Automated tests use temporary SQLite storage, fake Pi adapters, and fake clocks—no live model credentials. Priority acceptance scenarios: AT-01–05 (transport/lifecycle), AT-06–07 (pause/loops), AT-08–10 (authority), AT-11–15 (recovery/privacy/operation/install). These are planned checks, not completed tests.
