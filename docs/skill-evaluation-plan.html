Skill evaluation plan · simplified

Did the skill update actually make agents better?

We give no skill, the old skill, and the new skill the same coding tasks; run them through Pi, Codex, and Claude Code; then produce a clear recommendation backed by evidence.

💡

The whole idea: run a controlled experiment. First prove the skill helps at all, then prove the update is better without breaking anything important.

The process

Five steps, end to end

The evaluator handles setup and evidence collection so the person reviewing the update can focus on the result.

1

State the hypothesis

Name the behavior that should improve and what must not regress.

2

Choose versions

Prepare no-skill, current-skill, and proposed-update runs.

3

Run the same tasks

Use clean copies of test projects across each harness and model.

4

Check the work

Run objective checks first, then a blind qualitative review.

5

Compare & decide

Highlight skill lift, update gains, regressions, flakiness, and cost.

How the proposed tool fits

Plan together, run consistently, review the evidence

The agent helps design the evaluation. The runner executes the approved plan without improvising. Teammates make the release decision from the resulting evidence.

Who stays in control

Pi controls the run; automation has narrow authority

The controller watches objective execution state. A separate Pi supervisor reviews patterns at checkpoints and advises the person running the evaluation.

π

Pi control surface

/skill-eval provides a guided picker plus direct commands to validate, start, monitor, pause, resume, cancel, report, and delete runs. The monitor shows a selectable live redacted assistant-and-tool summary for every active agent. New Pi sessions receive one startup notification when a run is active.

⚙

Deterministic controller

A detached TypeScript worker survives Pi exiting and owns the queue, strict paired blocks, isolated workspaces, limits, objective checks, event-sourced state, and compact artifacts.

◇

Advisory supervisor

Read-only Pi sessions review preflight, critical anomalies, a blind final comparison, and a separate unblinded synthesis. They advise but never control the run or change deterministic evidence.

Automatic: explicit policies enforce timeouts and optional evaluation budgets. Cells are never retried automatically, and deterministic failures do not stop the remaining matrix.
Advisory: the supervisor identifies suspicious patterns and cites the run cells that support its recommendation.
Human-owned: changing the plan, following an advisory recommendation, and accepting or rejecting the update.
Fair comparison

Same task. Same model. Three configurations.

Each configuration runs in its own disposable workspace. The installed global skill is never changed, and the agent cannot see the answer key.

What you provide

The evaluator needs six things

①

Baseline + local candidate

The baseline is a committed Git ref. The candidate may be another ref or an explicit local snapshot, frozen before the run so uncommitted refinement stays practical and auditable.

②

What should improve

A short list based on the diff and release notes. This keeps the evaluation focused.

③

Representative tasks

Small synthetic cases for precision plus real repositories for realism.

④

Success criteria

Tests, expected behavior, forbidden changes, and any human-quality rubric.

⌘

Harnesses & models

Pi, Codex, and Claude Code, with a small named model set for each run profile.

$

Run profile

Exact models, thinking levels, repetitions, concurrency, timeouts, and an optional evaluation cost ceiling keep execution controlled.

What gets checked

Six questions, not one magic score

↪

Did it activate?

Did the agent load the skill when relevant—and avoid it when irrelevant?

✓

Was it followed?

Did the agent use the process, constraints, and references the skill specifies?

⚙

Did the result work?

Builds, tests, assertions, and focused diffs provide the strongest evidence.

↔

Did it travel well?

Does the skill load and behave sensibly across all three harnesses?

◷

What did it cost?

Track time, turns, tokens, infrastructure errors, and failures alongside quality. Cells are not retried automatically.

!

Did anything regress?

A critical regression should block an update even if the average score rises.

When you want more detail

Technical notes

These details matter during implementation, but they do not need to be understood to review the overall plan.

What makes a good hypothesis?

It names one observable behavior to move and one safeguard. For example: “The updated concurrency skill should identify actor-isolation problems earlier, without reducing build success or introducing unnecessary edits.” Release-note claims become test cases.

How do we avoid contaminating a run?
  • Use a temporary home and fresh fixture worktree for every run.
  • Inject no skill or exactly one frozen skill version; suppress ambient skills, extensions, prompts, and host context.
  • Load fixture-owned context explicitly, while keeping prompts, answer keys, and grading data outside the agent’s accessible workspace.
  • Create every cell from the same frozen prepared fixture and block remote pushes.
  • Keep an optional separate “ambient” suite for testing with real global configuration.
What tasks belong in the suite?

Begin the MVP with three to five tasks, then grow toward a focused set of 10–20 based on real failures:

  • Explicit: directly request the skill.
  • Implicit: describe the exact need without naming the skill.
  • Contextual: add realistic noise around the same need.
  • Negative: use an adjacent request where the skill should not activate.
  • Real repositories: vary project shape so fixtures do not flatter the change.
How do we handle nondeterministic model behavior?
  • Repeat important scenarios explicitly in the standard profile; infrastructure errors are never retried automatically.
  • Use recorded, seeded paired blocks so control, baseline, and candidate stay balanced and no arm consistently runs last.
  • Report pass rates, errors, and flaky cases instead of hiding them behind an average.
How is the work graded and compared?
  • An executor runs each task headlessly and captures its trace and artifacts.
  • A grader applies deterministic checks first; a judge cannot overrule a failed build.
  • A blind comparator reviews qualitative differences without knowing which skill version produced them.
  • An analyzer looks for patterns that aggregate scores hide.
  • Human review handles critical regressions, disagreements, or security-sensitive behavior.
How does the advisory supervisor work?
  • The deterministic controller—not an LLM—monitors process state, limits, artifacts, and objective checks.
  • A one-shot preflight advisor reviews the frozen plan before approval; a persistent blind Pi session resumes only for critical anomalies and final blind review.
  • A separate fresh unblinded synthesizer receives the arm mapping only after the blind finding is persisted.
  • All findings cite IDs from a generated redacted evidence bundle and use a finite advisory recommendation vocabulary.
  • Advice is recorded and shown in the monitor, but cannot alter the plan, grades, thresholds, spending policy, controls, or verdict.
What does each harness adapter need to do?
  • Select a model and run noninteractively.
  • Inject a skill from a temporary path.
  • Capture output, tool activity, timing, usage, and errors.
  • Normalize those records into one common result format.
What should be saved?

Private run state lives under ~/.pi/agent/skill-evals/. Each run retains an event ledger, projected state, resolved plan, Markdown/JSON reports, frozen skill inputs, fixture provenance, checks, diffs, and redacted traces. Disposable workspaces and dependency trees are removed after evidence capture; runs remain until explicit deletion.

What did the four articles change in this plan?
  • StackHawk: sharpen the hypothesis, use real repositories, hide the answer key, and let objective evidence outrank the blind judge.
  • DeepEval: treat this as an offline development evaluation—not a runtime guardrail—and organize it around datasets, traces, and metrics.
  • OpenAI: cover explicit, implicit, contextual, and negative activation; capture structured events; and keep checks small and explainable.
  • Tessl on Anthropic: add the no-skill control and separate execution, grading, blind comparison, and pattern analysis.
