Pi skill evaluation · milestone 1

Run a fair, durable test of a skill update.

Compare no skill, a committed baseline, and a frozen candidate against the same tasks. Pi prepares the experiment, runs it in the background, grades deterministic evidence, and keeps an auditable private report.

The whole workflow at a glance

Before you begin

What you need

π

The package loaded in Pi

Install this repository with pi install ., or use pi install -l . for project-only use. Run /reload after extension changes.

◇

An exact Pi model

The selected profile must name an available provider/model and explicit thinking level. Provider credentials must already work in Pi.

⌁

Reproducible inputs

You need a Git-backed skill source, a committed baseline ref, a local or committed candidate, and local or immutable Git fixtures.

Start with a small smoke profile.

Use one representative model, one repetition, and a few critical scenarios. Expand the matrix only after the suite proves useful.

Step 1 · Author

Separate the reusable test from this release

A suite describes how the skill is tested over time. A comparison describes the baseline, candidate, hypotheses, selected scenarios, and release gates for one change.

suite.yaml

Reusable evaluation contract

  • Skill source and path
  • Profiles, models, thinking, and repetition
  • Scenarios, prompts, fixtures, tools, and permissions
  • Deterministic checks and qualitative rubrics
comparisons/*.yaml

One proposed update

  • Committed baseline and frozen candidate
  • Change summary and hypotheses
  • Explicit scenario and profile selection
  • Exploratory or gated acceptance policy
Recommended layout
evals/
└── my-skill/
    ├── suite.yaml
    ├── prompts/
    ├── fixtures/
    │   └── focused-project/
    └── comparisons/
        └── main-to-local.yaml

Start from the bundled suite template and comparison template. For schema details and scenario-design advice, use the authoring guide or ask Pi to use the skill-eval-planner skill.

Understand the three arms

Control

No evaluated skill

Shows what the model can do without the skill. This keeps an easy task from looking like skill improvement.

Baseline

Committed trusted ref

Measures the current skill. The ref is resolved and frozen before approval.

Candidate

Local snapshot or ref

Measures the proposed update. Local files are copied, hashed, and frozen before approval.

Baseline − Control = current skill lift   ·   Candidate − Baseline = update gain   ·   Candidate − Control = candidate skill lift

Choose acceptance deliberately

Exploratory

Gather evidence first

A complete run ends with an informational verdict. Use this while learning reasonable thresholds.

Gated

Apply release rules

Typed deterministic rules produce pass, fail, or incomplete. Do not invent thresholds merely to make the file runnable.

Steps 2–3 · Validate and approve

Inspect the resolved experiment before spending

validate parses both files strictly, resolves refs, freezes skill inputs, materializes each disposable fixture, runs its trusted setup, then validates and freezes the prepared fixture. It verifies the selected Pi model, computes the candidate diff, and expands the exact cell matrix. It does not start evaluated cells.

Pi reports fixture-preparation phases while validation runs. Successful validation diagnostics are discarded; a failed preparation preserves its redacted setup log, structured phase timeline, and failure summary under ~/.pi/agent/skill-evals/diagnostics/.

Validate without running
/skill-eval validate evals/my-skill/comparisons/main-to-local.yaml

# Explicitly test another profile without changing the comparison:
/skill-eval validate evals/my-skill/comparisons/main-to-local.yaml --profile smoke

Before approving a run, verify:

  • The baseline ref is the trusted version you intended.
  • The candidate digest represents the intended local snapshot or ref.
  • The selected scenarios and total cells are affordable.
  • The exact provider, model, thinking, and repetition are correct.
  • Agent tools, write mode, and network permission are appropriate.
  • Every trusted setup command and its network permission are expected.
  • Best-effort isolation is acceptable for these fixtures.

Setup is trusted host code.

It runs once per scenario after approval, may inherit your host environment, and receives network only when the suite explicitly sets network: true. Evaluated agents use a separate sanitized environment and do not receive setup credentials.

Step 4 · Run and control

The controller keeps working after Pi exits

After approval, Pi starts a detached controller and returns immediately. Only one top-level evaluation can run globally. Another Pi session can reconnect by run ID—or omit the ID to use the active or latest run.

/skill-eval status [run-id]Show lifecycle, verdict, controller health, progress, cost, failures, isolation, and run directory.
/skill-eval pause [run-id]Stop dispatching new cells. Active cells finish before the run reaches paused.
/skill-eval resume [run-id]Continue a paused or pause-requested run.
/skill-eval cancel [run-id]Confirm immediate, irreversible cancellation. Active model processes are terminated.
Failures do not stop the matrix.

The controller records deterministic failures and continues collecting evidence. Provider and infrastructure errors are not retried automatically.

Closing the dashboard is not cancellation.

q, Esc, or Ctrl+C closes monitoring only. Use cancel or press c and confirm inside the monitor to stop the run.

Live dashboard

Watch progress without spending another model call

/skill-eval monitor [run-id] opens a model-free command center that polls state and live local process telemetry about once per second. It shows the controller and evaluated-agent process tree; select an active agent for its real stdout/stderr while the monitor is open.

Overview

Run metadata plus a selectable live summary of every active agent’s latest assistant or tool activity.

Processes

The controller and evaluated-agent process tree, with PID, parent PID, CPU, RSS, elapsed time, and command.

Live agent detail

Real stdout/stderr received after the monitor connects, with continuously updated elapsed time, tokens, cost, status, and last tool. Raw output is memory-only; completed cells retain the redacted timeline instead.

Matrix

Adjacent control, baseline, and candidate status for every seeded paired block.

Findings

Non-passing deterministic checks and acceptance-rule status.

Events

The latest lifecycle events without prompt, response, or tool-argument bodies.

Step 5 · Interpret

Read lifecycle, evidence, and verdict separately

A controller can finish cleanly while a candidate fails its gates. Conversely, an interrupted run may preserve enough evidence to prove a failure while still being incomplete overall.

Pass

All required evidence exists and every gated acceptance rule passed.

Fail

At least one deterministic gate definitively failed.

Incomplete

Required evidence is missing and no stronger definitive failure decides the result.

Informational

An exploratory run completed; no release gates were configured.

ResultMeaning
Cell passedThe harness completed and all critical deterministic checks passed. Advisory checks may still have failed.
Cell failedAt least one critical deterministic check failed.
Cell erroredThe harness, provider, timeout, or grading infrastructure failed; this is missing behavioral evidence, not a retry.
Not run / cancelledThe cell was never completed because of budget exhaustion, cancellation, or interruption.
Critical checkContributes to cell pass/fail and may decide gated acceptance.
Advisory checkAppears as a finding but does not by itself fail the cell.
/skill-eval report [run-id]Display the completed Markdown report in Pi.
/skill-eval monitor [run-id]Reopen a terminal run and inspect its matrix, findings, events, and redacted cell traces.
/skill-eval delete <run-id>Permanently remove a terminal run and its audit bundle after confirmation.
Review the evidence, not only the headline.

Check candidate failures, baseline-to-candidate regressions, no-skill lift, errors, warnings, costs, and the frozen provenance. Qualitative rubrics are retained but ungraded in milestone 1.

Private by default

Know what is retained

Authoritative runtime data is global and outside evaluated repositories. Runs remain until you explicitly delete them; disposable workspaces and prepared dependency archives are removed at finalization.

~/.pi/agent/skill-evals/ ├── registry.json └── runs/<run-id>/ ├── events.jsonl authoritative lifecycle ledger ├── state.json atomic current-state projection ├── controller.json PID, version, and heartbeat ├── resolved-plan.json immutable expanded matrix ├── report.md human-readable result ├── report.json machine-readable result ├── control/ atomic pause/resume/cancel requests └── artifacts/ frozen inputs, manifests, diffs, check logs, and redacted traces
Retained

Compact audit evidence

Frozen skill inputs, fixture provenance, setup definition/logs, manifests, generated diffs, deterministic results, reports, and bounded redacted traces.

Removed

Disposable execution state

Per-cell workspaces, isolated grading copies, post-agent archives, and prepared fixture archives containing installed dependency trees.

Redacted does not mean safe to publish blindly.

Artifacts are private and may contain model output, source diffs, fixture content, or values the redactor cannot recognize. Review every file before sharing it.

Isolation is best-effort in milestone 1.

Ambient Pi skills, extensions, templates, and host context are disabled; tools and paths are guarded; pushes and known dangerous or network commands are blocked. This is not a complete operating-system sandbox.

Troubleshooting

Common recovery paths

Validation reports several YAML errors

The parser is intentionally strict and reports unknown fields, missing required fields, duplicate IDs, unsupported tools or checks, invalid profile targets, and comparison-to-suite mismatches together. Correct the authored files rather than expecting unsupported fields to be ignored.

The selected model or thinking level is unavailable

Use an exact Pi provider/model visible to the installed Pi version and an explicitly supported thinking level. Confirm provider authentication outside the evaluation, then validate again.

Another evaluation is already active

Only one top-level run is allowed globally. Use /skill-eval status or /skill-eval monitor. Let it finish, cancel it, or finalize it if its controller is stale.

Pi says the controller is stale, dead, or missing

Run /skill-eval status [run-id]. Pi offers to finalize the run as interrupted, terminate matching child processes, mark unfinished cells as errored or not run, preserve partial evidence, write reports, and release the global slot. It does not resume crashed work automatically.

The run paused later than expected

Pause is checkpoint-safe, not an immediate kill. It stops new dispatch, lets the currently active batch finish, and then enters paused. Use cancellation only when active cells must stop immediately.

The run completed with an incomplete verdict

Look for errored, cancelled, or not-run cells and not_evaluated acceptance buckets. Common causes are provider errors, timeouts, cost-budget exhaustion, cancellation, or controller interruption. The runner intentionally does not hide these with retries.

A fixture uses submodules or Git LFS

Git submodules and unresolved Git LFS pointer files are rejected in milestone 1. Materialize the required fixture content directly in a small local fixture or a pinned repository that does not depend on those mechanisms.

The report is not available yet

Reports are written when a run completes, is cancelled, or is finalized as interrupted. Use status or monitor while it is active.

Run ID is usually optional.

Without one, Pi chooses the active run or the latest retained run. A unique run-ID prefix is also accepted.

Current milestone boundary

Milestone 1 runs Pi targets and deterministic checks. Codex, Claude Code, advisory LLM supervision, qualitative judging, HTML report export, custom grader scripts, Git submodules, and Git LFS fixtures are not yet supported. Unsupported configuration fails validation rather than being silently skipped.
